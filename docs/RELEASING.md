# Выпуск готового GigaFlow

Релиз для пользователей — DMG с переносимым `GigaFlow.app`, встроенными Python, MLX и моделью GigaAM. Пользователь перетаскивает приложение в Applications и выдаёт разрешения; сборка, установка Python и скачивание модели при первом запуске не требуются.

Текущая сборка предназначена для **Apple Silicon и macOS 26.2+**. Это требование закреплённых нативных библиотек MLX. `bundle-runtime.py` читает deployment target каждого Mach-O и записывает максимальную нижнюю границу в `runtime-manifest.json`; сборщик DMG переносит её в `LSMinimumSystemVersion` приложения.

## Подготовка Mac издателя

Нужны Xcode Command Line Tools, проверенная среда `~/Developer/gigaam-pilot` с версиями из `requirements.lock.txt` и установленная модель закреплённой ревизии. Упаковщик текущего релиза ожидает CPython **3.11.18 из python-build-standalone 20261026**: источник архива и SHA256 указаны в `scripts/runtime-licenses/PythonBuildStandalone/SOURCE.json`. Произвольная установка Python 3.11 для выпуска DMG не подходит.

Перед упаковкой выполните проверки из корня репозитория:

```sh
GIGAFLOW_TEST_PYTHON="$HOME/Developer/gigaam-pilot/.venv/bin/python" bash scripts/check.sh
```

Сборщик использует постоянную локальную идентичность издателя из `~/Library/Application Support/GigaFlow/Signing`. Закрытый ключ, пароль связки ключей и её файл остаются на Mac издателя. Их нельзя добавлять в репозиторий, DMG или Release assets. Обычная подпись приложения содержит публичный сертификат; это не закрытый ключ.

Для очередного релиза используйте прежнюю идентичность. Не запускайте регенерацию сертификата и не подменяйте её ad-hoc подписью. Создание своей новой идентичности через `app/setup-signing.py` относится только к первоначальной настройке независимого издателя, а не к обновлению официальной серии выпусков.

С версии 0.4.0 нужны также постоянные ключи подписи обновлений Sparkle. Закрытый ключ находится в `~/Library/Application Support/GigaFlow/UpdateSigning/private-key.base64`, вне репозитория. `SUPublicEDKey` в `app/Info.plist` содержит только публичный ключ. Для очередного выпуска сохраняйте эту пару; не создавайте замену ключа. Проверка существующей идентичности и подготовка подписанной ленты описаны в [UPDATES.md](UPDATES.md).

## Сборка

Обновите версию и увеличьте номер сборки в `app/Info.plist` (для 0.4.0 — сборка 8), затем выполните:

```sh
bash scripts/build-release.sh
```

Для версии `0.4.0` результат находится в:

```text
dist/GigaFlow-0.4.0-arm64.dmg
dist/SHA256SUMS.txt
dist/release-0.4.0/image/GigaFlow.app
```

Скрипт не перезаписывает уже существующий результат релиза. Для повторной сборки переместите предыдущие файлы из `dist` в отдельную папку.

Сборка создаёт иконку, компилирует приложение, копирует runtime и лицензионные уведомления, добавляет Hammerspoon-модуль и Sparkle 2.10.1. Архив Sparkle закреплён по SHA256 в `scripts/fetch-sparkle.sh`; инструменты издателя остаются в `vendor/`, в приложение попадает framework с его помощниками и лицензией. Вложенный нативный код и компоненты Sparkle подписываются перед внешним приложением. Исходная рабочая среда и установленное приложение не заменяются. DMG также содержит ссылку на Applications и краткую инструкцию установки.

Собрать runtime отдельно можно так:

```sh
python3 scripts/bundle-runtime.py \
  --source "$HOME/Developer/gigaam-pilot" \
  --destination "$PWD/dist/prepared-runtime"
```

Папка назначения должна отсутствовать. После проверки этой среды сборщик умеет использовать её повторно:

```sh
GIGAFLOW_BUNDLED_RUNTIME="$PWD/dist/prepared-runtime" bash scripts/build-release.sh
```

Упаковщик сверяет версии пакетов с lock-файлом, проверяет архитектуру и пути зависимостей нативных библиотек, сохраняет лицензии и исключает кеши, bytecode и пути компьютера сборки. Готовый runtime не является копией virtualenv с абсолютными ссылками на Python издателя.

## Проверка готового артефакта

До публикации проверьте:

1. `codesign --verify --deep --strict` для приложения и подписи вложенных Mach-O; затем `hdiutil verify` для DMG. Основные проверки уже вызываются сборщиком.
2. Запуск скопированного приложения из другой папки: `--runtime-info` должен показывать режим `bundled` и пути только внутри этой `.app`.
3. Распознавание тестового аудио встроенной средой без обращения к среде разработки, системному Python или сети. Проверку проводите также после финальной подписи: bundle не должен измениться от кешей или bytecode.
4. Установку из DMG и путь первого запуска, включая штатное разрешение Gatekeeper и выдачу доступа к микрофону и Универсальному доступу. Проверка на компьютере издателя не заменяет проверку на другом Mac.
5. Отсутствие записей пользователя, журналов, секретов и личных путей в образе; наличие полного runtime и лицензионных уведомлений.
6. Обновление с предыдущей совместимой версией: подпись архива и ленты, загрузку, отсрочку во время диктовки и ожидания копирования, замену в прежней папке, перезапуск и сохранение разрешений. Проверки политики перезапуска не заменяют проверку реального обновления.

Проверка путей без запуска модели:

```sh
"dist/release-0.4.0/image/GigaFlow.app/Contents/MacOS/GigaFlow" --runtime-info
```

Не публикуйте результаты проверок с абсолютными путями пользователя. В Release notes указывайте только выполненные проверки и фактические ограничения.

## Подпись и первый запуск

Текущие выпуски используют собственный постоянный сертификат издателя, **не Developer ID**, и **не нотарифицированы Apple**. Контейнер DMG не имеет подписи Apple; приложению и вложенному коду назначаются проверяемые подписи. Отдельно Sparkle проверяет Ed25519-подпись архива до распаковки и подпись ленты обновлений. SHA256 образа также публикуется рядом с ним.

Если macOS блокирует первое открытие, пользователь может разрешить именно GigaFlow через **System Settings → Privacy & Security → Open Anyway**, как описано в [инструкции Apple](https://support.apple.com/en-gb/102445). Не добавляйте в установщик команды снятия quarantine, отключения Gatekeeper или изменения доверия корневым сертификатам пользователя.

Для будущего нотарифицированного релиза потребуется Developer ID Application, подходящие настройки Hardened Runtime, secure timestamp, отправка через `notarytool` и stapling результата. Self-signed сертификат для notarization не подходит. Изменение сертификата требует отдельно проверить миграцию разрешений и идентичности обновлений. [Требования Apple](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

## Публикация на GitHub

После окончательной проверки DMG подготовьте подписанную ленту:

```sh
bash scripts/make-appcast.sh dist/GigaFlow-0.4.0-arm64.dmg
```

Если предыдущая подписанная лента не лежит в `dist/appcast.xml`, передайте её вторым аргументом. Скрипт сохраняет предыдущие выпуски, сверяет метаданные реального DMG и подписывает архив и ленту прежним ключом. Результат — `dist/appcast.xml`; после его создания нельзя изменять DMG.

Зафиксируйте исходники, по которым собран артефакт. Создайте **черновик** релиза для этого коммита и загрузите сразу три файла: **DMG, SHA256SUMS.txt и appcast.xml**. Проверьте завершение загрузки, размеры и контрольные суммы, затем опубликуйте релиз как Latest. Только после этого лента должна указывать пользователям на новый выпуск.

Постоянный адрес ленты — `https://github.com/aspalagin/GigaFlow/releases/latest/download/appcast.xml`. Поэтому **каждый** следующий Latest-релиз обязан содержать корректный подписанный `appcast.xml` вместе с установщиком. Отсутствующий файл нарушит проверку обновлений. Не редактируйте подписанный XML вручную. Не загружайте рабочую папку, Python-окружение издателя или материалы подписи. Подробности — в [UPDATES.md](UPDATES.md).

GitHub требует, чтобы каждый Release asset был меньше 2 GiB; сборщик проверяет размер DMG. [Ограничения GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

В описании релиза укажите версию, Apple Silicon, macOS 26.2+, фактический размер скачивания, включённую модель, порядок первого запуска и отсутствие notarization. Для перехода с 0.3.1 и более ранних версий нужна одна ручная установка 0.4.0: в старых версиях ещё нет механизма обновлений. Ссылка на последнюю версию в README ведёт на `releases/latest`; имя DMG в инструкции нужно обновлять вместе с версией.
